Resonance docs

Install the platform locally, log metrics and audio from your training loop, and configure, test and operate every service.

InstallOne command brings up the full stack. Python SDKLog metrics and audio without blocking training. ConfigurationEvery environment variable, per service.

Requirements

Resonance runs its data stores in Docker and its services on your machine. You need:

ToolVersionUsed for
Docker with Compose v2recentPostgres, two ClickHouse nodes and Keeper, MinIO, Redpanda, Redis
Python3.10 or newer; 3.11 or 3.12 recommendedControl API, audio workers, SDK. Very new releases (for example 3.14) may not have NumPy or soundfile wheels yet.
Go1.22 or newerIngest and media gateways, built by make up
Node.js and npm20 or newerWeb UI (Vite)
libsndfileanyUsed by soundfile to read and write audio. CI installs libsndfile1 on Linux; install it if import soundfile fails.

Memory

The stack runs a lot of containers. Give Docker generous memory; Redpanda is already capped at 1 GB so it doesn't starve the rest.

Install and run

  1. Clone the repository.

    terminal
    git clone https://github.com/mishraprafful/resonance
cd resonance

  2. Bring everything up. The first run takes a few minutes.

    terminal
    make up

    make up starts the data stack in Docker and waits up to about two minutes for it to be ready. It then creates .venv with the API, workers and SDK, runs npm install in src/ui/, builds both Go gateways, and starts ingest, media, API, worker and the web UI. Logs and PID files go to .run/.

    To pick a specific Python, run PYTHON=python3.12 make up.

  3. Open the UI at http://localhost:5280 and create the admin account (see First login).

  4. Load sample data so there's something to look at.

    terminal
    make demo

Local only

The dev stack ships with fixed development credentials. Never expose it to a network. See Deploying before running it anywhere else.

First login

On a fresh install the UI asks you to create the platform admin. That account owns the default dev team and can administer every team.

  • Everyone else signs up and either creates a new team (they become its owner) or asks to join an existing one. Join requests stay pending until a team owner or admin approves them on Account & teams.
  • A team is the tenant boundary. Projects, runs, audio and datasets belong to the active team. Switch teams from the sidebar.
  • Local SDK runs need no token. With dev-open mode on (the local default), runs without credentials land in the dev team, which the admin sees.

Install the SDK

The SDK isn't on PyPI yet. Install it from a clone, into the venv make up created or your own training environment:

terminal
pip install -e "./sdk[audio]"
resonance version

The audio extra adds soundfile, which you need to log NumPy arrays. The import name is resonance.

Quickstart

train.py
import resonance

run = resonance.init(
    project="vocoder",
    name="hifigan-lr3e-4",
    config={"lr": 3e-4, "batch_size": 16},
)

try:
    for step in range(10_000):
        loss = train_step()
        run.log({"loss/mel": loss}, step=step)

        if step % 500 == 0:
            audio = generate_sample()
            run.log_audio(
                "samples/val", audio, sample_rate=22050, step=step,
                caption=f"step {step}", reference=reference_audio,
            )
except Exception:
    run.finish(state="crashed")
    raise
else:
    run.finish()
  • log and log_audio return immediately; batching and uploads run on a background thread.
  • Always call finish(). It flushes what's queued and waits up to 30 seconds. The flush thread is a daemon, so a script that exits without finish() can lose its last data.
  • Re-logging the same reference uploads nothing: identical audio is detected by hash and stored once.

Offline and online

Set the mode with RESONANCE_MODE. The default is offline.

Offline

No network calls. Events are appended to .resonance/<run-id>/events.jsonl: run start and finish, metrics, and audio metadata with content hashes. Raw audio bytes are not spooled, and there's no command to upload an offline run later yet.

Online

  • init registers the run with the control API and raises if the API is unreachable.
  • Metrics go to the ingest gateway in batches of up to 1,000 points, at least every 2 seconds.
  • Audio is hashed, checked for an existing copy, uploaded straight to object storage with a presigned URL when it's new, then registered. Bytes never pass through the API.
  • Online runs also keep the local spool as a log. Upload errors are recorded there as error events instead of interrupting training.
Settings are read at import

Set RESONANCE_* variables before import resonance, or pass a Settings object to init.

SDK reference

resonance.init(project, *, config=None, name=None, settings=None)

Starts a run and returns a Run. In online mode the project is created if it doesn't exist. name defaults to run- plus the first characters of the run id.

Run.log(metrics, *, step=None)

Logs a dict of scalar metrics. Values are converted with float(). Pass step explicitly; an omitted step is recorded as 0.

Run.log_audio(key, audio, *, sample_rate, step=None, caption=None, reference=None)

  • audio is a NumPy array (encoded to WAV; needs the audio extra) or a path to a file (uploaded byte for byte). Use WAV or FLAC files so the worker can derive waveforms and spectrograms.
  • reference takes the same types and is shown next to the output in the UI.
  • Encoding and hashing happen on the calling thread; the upload happens in the background.

Run.log_dataset(name, source)

source is a directory (searched recursively for .wav .flac .ogg .mp3 .opus), a single file, or a list of paths or {"path": ...} dicts. The version id is derived from the content, so the same files always produce the same version, and files already stored upload nothing. Online mode only.

Run.finish(state="finished")

Flushes, marks the run with state (for example finished or crashed) and closes the client.

Auth and API tokens

Requests authenticate with a Bearer API token or a browser session. Locally, dev-open mode (RESONANCE_DEV_OPEN=true, the default) treats requests without credentials as the owner of the dev team. Turn it off anywhere but your laptop.

Create a token for your team

Tokens look like rsn_…, are stored hashed, and are shown once. There's no token screen in the UI yet, so use the API. Log in with an owner or admin account and keep the session cookie. The password is read from a prompt so it stays out of your shell history:

terminal
read -rs RSN_PASSWORD
printf '{"username":"alice","password":"%s"}' "$RSN_PASSWORD" |
  curl -s -c cookies.txt -X POST http://localhost:8000/v1/auth/login \
    -H 'content-type: application/json' --data @-

The response includes current_org, your active team id. Create the token for that team:

terminal
curl -s -b cookies.txt -X POST http://localhost:8000/v1/orgs/$ORG_ID/tokens \
  -H 'content-type: application/json' -d '{"name":"laptop","role":"member"}'
rm cookies.txt

Copy the token field into your secret manager, then export it as RESONANCE_API_TOKEN where training runs. Don't commit it. List tokens with GET /v1/orgs/{org_id}/tokens and revoke one with DELETE /v1/orgs/{org_id}/tokens/{token_id}.

Web UI tour

  • Projects: every project in the active team. Create one here, or just log a run and it's created for you.
  • Runs: a table or cards with best-metric stats, search, state filters and sparklines.
  • Run detail: live metric charts, config and system panels, and generated audio with a step slider, waveform, spectrogram and playback.
  • Compare: overlaid metrics, a synced A/B player that always plays original quality (with a blind-test mode that records ratings), and a prompt grid.
  • Gallery: every sample as a spectrogram tile, filtered by run, latest step or all steps.
  • Datasets: content-addressed dataset versions and their files.
  • Account & teams: create, join and switch teams, approve join requests, and delete projects or teams (admins).
  • Tweaks: the button at the bottom right (or ⌘. / Ctrl+.) sets theme, accent, spectrogram colormap, chart style, density, navigation layout and runs view.

Storage and quotas

How audio is stored

  • Content-addressed: every file is keyed by its SHA-256 under the team's prefix, so identical content is stored once per team.
  • Direct upload: clients upload with presigned URLs; the API never handles audio bytes.
  • Derivations: workers compute waveform peaks, spectrograms and probes. New assets are queued on Redpanda, with a Postgres poll as a backstop so nothing is missed.
  • Playback: through the media gateway (HMAC-signed, range requests, CDN-cacheable) when MEDIA_PUBLIC_URL is set, otherwise presigned links.

Lifecycle tiers

A worker sweep moves assets hot → ia after 30 days and → archive after 90 days without access. Playing an asset warms it back to hot. Nothing is ever deleted. Each object is tagged resonance-tier=<tier>; add a bucket lifecycle rule on that tag to move the storage class in S3 or GCS. Team admins can override the thresholds:

terminal
curl -s -X PUT http://localhost:8000/v1/orgs/$ORG_ID/lifecycle \
  -H "authorization: Bearer $RESONANCE_API_TOKEN" \
  -H 'content-type: application/json' -d '{"ia_days": 14, "archive_days": 60}'

An empty body restores the platform defaults. GET /v1/org returns storage used, the quota and asset counts per tier.

Quotas and rate limits

  • Storage quota: set with storage_quota_bytes when a team is created through POST /v1/orgs. Uploads past it get 413. Teams created in the UI have no quota.
  • Rate limit: requests per team per minute, set globally with RESONANCE_RATE_LIMIT_PER_MIN (default 600; 0 turns it off). Over the limit returns 429.
  • Backpressure: the ingest gateway answers 503 when its buffer is full instead of slowing down.

Gateways

  • Ingest POST /v1/metrics: accepts a batch of points for a run and returns 202, or 503 when the buffer is full.
  • Media GET or HEAD /v1/stream/<key>?exp=&sig=: range-streams an original. Returns 206 for partial requests and 403 for a bad or expired signature.

Performance numbers are earned, not asserted: a capacity figure goes into the README only after a passing load test on the reference rig described in loadtest/README.md. The gates are metric ingest p95 under 50 ms, upload preparation p95 under 75 ms and errors under 0.1%.

Deploying

Today Resonance ships a Docker Compose development stack only. Container images, Helm charts and Terraform for Kubernetes are planned but not in the repository yet. If you run it beyond a laptop, at minimum:

  • Replace every development credential: Postgres (including the resonance_app role), ClickHouse, the object store and MEDIA_SIGNING_SECRET. Remove the seeded dev-owner token created by deploy/dev/postgres/init.sql.
  • Set RESONANCE_DEV_OPEN=false.
  • Run the API as resonance_app so row-level security applies; only the workers use a superuser connection.
  • Keep the ingest gateway on a private network: it doesn't authenticate requests yet.
  • Serve everything over HTTPS; the session cookie doesn't set the Secure flag.
  • Set MEDIA_PUBLIC_URL and a shared signing secret to stream through the media gateway and a CDN.
  • Add a bucket lifecycle rule on the resonance-tier tag if you want storage-class transitions.

Known limitations

  • Offline runs can't be uploaded afterwards yet.
  • System metrics (CPU, GPU, memory) aren't captured yet.
  • Login is username and password only; SSO/OIDC is planned.
  • No production deployment manifests yet.
  • The ingest gateway doesn't authenticate requests.
  • Rate limits are global; the per-team setting isn't applied yet.
  • Capacity figures are design targets until certified.
  • Video logging is planned.
